# Marco TV 项目评估与优化方案

作者：**Pilipala** · 评估日期：**2026-10-27** · 当前版本：**0.11.1**

评估基线：源码提交 `1bfe102`。本轮核对菜单定义、导航与设置存储、绘制和异步任务、系统集成、备份诊断、构建与文档，并运行现有本地检查。本轮未安装新 APK、改动电视权限或执行重启、换网、任务清除；下文明确区分代码事实、改进建议和待测项目。

## 1｜整体结论

Marco TV 已具备较完整的个人电视桌面功能。当前主要问题是功能持续增加后，菜单归属、状态表达和系统能力入口变得分散。下一阶段应先整理现有体验，再扩展兼容性检测；不建议推翻已经验证过的桌面绘制和 Home 处理，也不建议同时引入账号、云同步等新系统。

当前可定位为「在已验证设备上可日常试用的开源桌面」，不能据单台电视记录宣传为多品牌全面适配或长时间稳定性已全部验证。

已有基础：

- 38 个 Java 源文件，约 3847 行；绘制、菜单、网络、媒体、任务、备份和诊断已拆分，不是全部堆在一个 Activity 中。
- 菜单顺序使用稳定条目 ID；隐藏、收藏、排序和备份均已有实现，重构应迁移配置，不能让用户重设。
- 图片有内存预算和低内存设备策略；后台时停止主要界面计时和动画，已有缓存失效处理。
- 备份有大小限制、格式及摘要校验、恢复前快照与中断回退；诊断默认仅保留本地。
- 系统任务辅助服务通过受权限保护的 Provider 和 Binder 交接，并校验调用 UID；不是任意网络客户端可调用的控制端口。这只是代码核对，不等于完整安全审计。
- 已有公开构建、签名验证、源码打包、许可检查、产品展示和操作文档。

## 2｜设置重复与分类核对

目前设置首页有 12 项。已查主菜单和五个可排序列表的定义，未见同一列表中重复声明同名选项；`MenuOrder.resolve()` 也会去重已有排序记录。已确认的主要问题是跨页面重复入口、相近名称和全局设置混入局部菜单。是否存在同一页偶发重复显示，需要另做实机复现，不能用源码检查排除。

| 项目 | 目前出现的位置 / 实际行为 | 判断与建议 |
| --- | --- | --- |
| 开机与默认桌面 | 设置首页；设备设置；状态页和引导中的快捷入口 | 首页与设备设置重复归属。统一归入「系统与启动」；状态页和引导保留「去设置」快捷跳转，共用同一页。 |
| 状态检查 | 设置状态与引导；本地诊断的一键检查；开机设置的运行状态；最近任务的服务状态 | 前两个进入同一状态页，后两个各有独有字段。统一状态中心，保留 ADB 端口、最近恢复、任务服务版本及移除能力，不能简单删掉其中一页。 |
| TV 应用排序方式 | 卡片外观；单独卡片设置 | 实际改变整行 TV 应用，且输入源卡片设置中也会出现。移到「应用与分类 → TV 应用排序」；局部菜单不再放未经说明的全局选项。 |
| 添加应用 | 左侧分类操作栏；卡片外观 | 外观页归属不合理。保留用户指定的左侧操作栏入口，另在应用管理页提供同一入口；不新增桌面加号卡片。 |
| 壁纸图库 / 更换本地壁纸 | 设置首页并列；壁纸亮度藏在图库 | 不是同一个功能，但可以合并为「壁纸」页，集中内置、本地、压暗程度和恢复默认。 |
| 恢复隐藏的卡片 | 首页独立项目；单卡隐藏；播放卡片又有恢复暂时隐藏的卡片 | 桌面隐藏与媒体临时隐藏是不同数据。桌面项收进应用管理，媒体项明确叫「恢复暂时隐藏的播放卡片」。 |
| 卡片圆角 | 桌面卡片外观；最近任务外观 | 各自独立参数，不应合并数值。改为「桌面卡片圆角」和「任务卡片圆角」，避免以为修改不生效。 |
| 亮度 / 暗度 | 壁纸亮度、壁纸压暗、屏保时间亮度、屏保背景压暗、任务背景暗度 | 范围不同，不是重复。背景统一用「压暗程度」，说明越大越暗；数字用「时钟亮度」，避免同一控件前后叫法相反。 |
| 向左移动 / 向右移动 / 拿起并移动 | 长按卡片菜单 | 操作效果重叠。优先保留「移动卡片」交互，左右移动作为可选快捷操作，不再占三个平级主项。 |
| 设备信息 / 关于 | 设备页和关于页 | 设备页保留品牌、型号、系统与固件；关于页保留软件版本、Pilipala、许可、免费与退款说明，不必重复展示整套信息。 |

## 3｜优先纠正的状态与操作文案

### 「检查」应保持只读

`SystemIntegration.show()` 的「立即检查 ADB」分支先执行 `recover()`，再显示状态。已有授权及恢复开关生效时，这会恢复 ADB 开关，并可能执行已启用的 Home 服务配置恢复，不只是检查。

建议拆成「查看连接状态」和「立即执行已启用的恢复」。前者不改系统配置；后者清楚说明执行范围，不再让名称暗示只读。最近任务的「检查任务服务」也调用 `configure()` 同步配置，应拆分状态查询与配置同步。

### 当前状态与点击动作分开

诊断页说明区的「自动记录：开启」表达当前状态，但按钮中的「自动记录：关闭」表达下一步动作。二者同时出现容易被误认为相互矛盾。

统一采用「自动记录：已开启」显示状态，操作写「关闭自动记录」。播放、Home、ADB、屏保等开关也使用同一套规则；开关已开启、权限已授予、服务已连接、实测已通过应分别表达。

### 唤醒恢复不要藏在任务外观中

「唤醒后恢复桌面」目前在最近任务设置中，还依赖 Home 兼容和任务辅助服务。建议放到「系统与启动」，在最近任务页保留解释及跳转。服务未连接时明确提示待启用，不能只显示一个已开启的偏好开关。

## 4｜建议的设置结构

首页由 12 项归并成 7 组。每组有唯一主入口，桌面齿轮、左侧分类栏和异常提示可保留情境快捷入口。

| 首页分组 | 二级内容 |
| --- | --- |
| 桌面与外观 | 壁纸；桌面卡片样式；时间与日期；屏保 |
| 应用与分类 | 添加应用；收藏与置顶；TV 应用排序；隐藏与恢复；分类显示 |
| 最近任务 | 双击 Home；立即打开；任务卡片样式；动画与手势；任务服务状态 |
| 正在播放 | 显示开关；权限；播放来源；恢复暂时隐藏的播放卡片 |
| 网络与声音 | Wi-Fi；媒体音量 |
| 系统与启动 | 默认桌面与 Home；开机打开；唤醒恢复；ADB 与授权；恢复原桌面 |
| 维护与帮助 | 状态与兼容性；备份与恢复；本地诊断；首次使用引导；设备信息；关于 Marco TV |

其中「分类显示」为建议扩展项，不作为当前已有功能宣传。分组名称与最终范围可在实现前统一；先落实去重和归属，再补非必需功能。

交互规则：

- 返回逐级退回父页，首页返回桌面；Home 直接回桌面。
- 刷新当前状态或切换开关不新增历史层级；返回保留父页焦点与滚动位置。
- 单张卡片菜单只放影响当前卡片的动作，全局排序移动到应用与分类。
- 配置列表统一支持排序；动态 Wi-Fi、应用搜索结果等按各自规则展示。
- 普通外观选项直接可用；需要授权的能力就近说明条件，并能跳转到正确设置页。
- 长说明放帮助或展开区，保留当前状态和关键操作在首屏，避免首屏全是说明、按钮落在下面。

| 优先级 | 工作 | 原因 | 完成标准 |

| P1 | 设置去重、全局 / 单卡职责分离、开关文案统一 | 已有明确的理解与操作成本 | 同一功能只有一个定义；快捷入口指向同页；检查按钮不执行恢复；主要操作无需猜测影响范围。 |
| P1 | 统一状态和能力数据 | 当前不同页各算状态，未来检测工具容易再复制一套 | 默认桌面、Home、ADB、媒体、任务均采用同一数据来源；明确偏好、授权、连接、实测四层状态。 |
| P1 | 菜单重组与旧配置迁移 | 用户已自定义菜单、排序和备份 | 0.11.1 配置覆盖升级后可保留；新增菜单 ID 与备份允许列表同步；老备份可恢复，不重置已有卡片和授权。 |

| P2 | 静止画面和辅助服务开销 | 存在可核对的周期性工作，但未测得收益 | 先有基线，再测总 PSS、CPU、帧耗时、打开延迟；减少工作后保持时钟、动画和唤醒正确。 |
| P2 | 新版系统与长期实测 | 当前公开证据集中在一台 Android 9 电视 | 至少补一台 Android 10 以上 Android TV / Google TV，分别测权限、Home、网络返回、文件选择；做持续运行与待机测试。 |
| P2 | 自动检查扩围与发布一致性 | 现有 CI 不覆盖所有菜单、状态和展示资源 | 增加导航 / 状态矩阵、备份迁移测试、HTML 和图片链接检查；版本、文档及检测规则一致。 |
| P3 | 高级外观预设、更多壁纸与语言 | 有价值但不能解决当前归属混乱 | 菜单稳定后按真实使用反馈增加，避免再堆一级入口。 |

### 性能：先测量再决定

源码确认的候选项：

1. `MainActivity` 每秒使整个 `HomeView` 重绘；时钟显示到分钟，画面静止时可以按分钟变化和相关事件刷新。动画仍需保留逐帧更新，不能为了省资源破坏过渡和媒体状态。
2. 任务辅助服务 `watchWake()` 每 500 毫秒检查一次交互状态，关闭唤醒恢复时循环仍存在。可评估按能力使用事件通知或延长空闲轮询，必须验证失联重连与唤醒时序。
3. 修改收藏、隐藏、改名等会触发应用列表重新加载；低内存机又会关闭额外图片缓存。可优先更新受影响数据，避免每个轻量编辑都重新发现全部应用。
4. `loadGeneration` / `wallpaperGeneration` 能丢弃过期结果，但不自动取消已排队的扫描或解码。可增加合并请求与前置过期检查。
5. 低内存策略不是「没有内存成本」：当前可见卡片仍持有图片，不能只看 LRU 大小判断总占用。

这些是源码观察，不是本轮测出的卡顿根因或性能提升。用相同 APK、相同应用数量、壁纸和操作脚本对比，记录中位数、峰值及异常；不预先承诺节省百分比。

建议场景：静止桌面、左右快速切换、最近任务展开、反复打开设置、导入壁纸、备份包含图片、待机唤醒。按场景分开统计，不把长期运行、冷启动与普通待机合为同一项。

## 6｜结构与兼容性方案

### 先统一定义，再调整界面

建议建立一份设置项描述：稳定 ID、显示标题、所属分组、作用范围、当前状态、前置能力、动作和预览类型。主菜单与快捷入口共用定义，不再靠多处字符串数组和数字下标分别维护。

当前 `TvDialog.pageKey()` 在缺少 orderKey 时使用显示标题作为页面身份。后续应改为独立页面 ID，避免改标题、增加语言或同名页面时影响返回行为。优先小步提取，不同时更换渲染框架。

`BackupStore` 对菜单顺序分组有明确允许列表，目前只有 main / clock / device / startup / cards。新增分组时必须同步校验与迁移，不能只改 UI，导致新的菜单顺序无法进入备份。

### 兼容性检测工具与应用共用核心

检测核心只产出能力与证据，不顺带修改系统。使用结构化状态，例如已通过、需要授权、需要实测、暂不支持、尚未验证，并保留测试版本、日期和来源。

独立检测 APK、Marco TV 的状态页和网页反馈使用相同报告结构。先完成基础设备参数、安装运行、绘制与遥控器的引导检测；Home、ADB、待机与任务能力按授权和用户主动测试逐项补齐。

不自动上传序列号、MAC、IP、Wi-Fi 名称、应用清单或观看内容。不根据品牌猜测工程菜单密码；地区和固件不同的记录不能直接视作同一适配结果。

当前 targetSdk / 编译 API 为 28。建议把新版系统兼容作为独立工作阶段，先检查 Wi-Fi、文件选择、包可见性、前台服务、广播和系统任务接口的实际表现，再决定升级策略，不在菜单整理中顺手提高目标版本。

本轮没有创建检测 APK、提交表单或新增多品牌通过记录；此前讨论仍属于待实现方案。

- 检查按钮不改系统；用户主动恢复时才执行相应配置。
- 产品页、图文版、模块数据、截图和下载链接同步。现有公开检查主要覆盖 Markdown 普通链接，HTML、图片链接和线上内容一致性应纳入自动检查。

## 8｜建议实施顺序

1. **设置整理版本**：去重与重新分组，修正文案，统一页面 ID 和状态入口，处理旧配置与备份迁移。完成完整菜单和实体遥控器回归后发布。
2. **兼容性检测版本**：共用检测核心、独立小工具、网页初筛与用户确认后的报告反馈，开始积累按固件划分的兼容记录。
3. **性能与稳定性版本**：先基线采样，再优化任务队列、静止重绘及轮询；增加新系统设备和长期运行验收。

每一阶段独立验收，保留回退方案。原厂桌面、Home 直接返回、方向键和待机恢复等已有关键行为优先保持；任何相关修改都要重新实测，不能只依赖编译成功。
