# Marco TV 动态壁纸与天气实施计划

Pilipala · 2026-11-03

状态：方案与任务分工；尚未实现新功能、安装测试包或发布新版本。

## 1. 产品范围

本轮交付两项可独立开关、独立验收的功能：

1. 天气：网络城市推荐、手动选择城市、首页天气、小气泡详情，以及后续手机定位辅助。
2. 动态背景：本地视频、手机上传、静态 / 仅屏保动态 / 桌面持续动态三种模式，随后评估 Apple 航拍素材源。

默认保留已有静态壁纸。用户启用动态背景时推荐“仅屏保动态”；持续动态由用户选择。第一阶段面向 Android 6.0+ 正常版和受限版；Lite 保持静态背景，天气支持另行评估，不把新依赖带进 API 14 共享文件。

第一版不加入实时雨雪粒子、HDR 动态桌面、任意播放速度、多视频同时播放、自动追踪精确位置。按昼夜和天气切换素材放到基础功能稳定之后。

## 2. 模型选择依据

OpenAI 官方模型选择指南将 Astra 定位于模糊问题和深入分析，将 GPT-6.1 Sol 定位于兼顾复杂任务与时间成本，将 GPT-6.1 Terra 定位于视觉推理、电脑操作及范围明确的代码修正。

以下是针对本项目的任务安排，不是模型之间的绝对能力排名，也不是性能或工期承诺。模型名称不能代替测试证据。

| 模型 | 本项目职责 | 建议推理档位 | 交付重点 |
| --- | --- | --- | --- |
| GPT-6 Astra | 架构、播放器生命周期、竞态、权限边界、关键故障和最终集成审阅 | High；难以复现的问题再用 Extra high | 明确状态转换、失败处理和实机证据 |
| GPT-6.1 Sol | 天气服务与客户端、素材下载缓存、手机上传、配置持久化、功能整合 | Medium；跨模块实现用 High | 接口闭环、可维护代码、错误与取消处理 |
| GPT-6.1 Terra | 已确定方案的 UI、焦点与布局检查、手机页面操作、局部修正、文档与素材核对 | Medium；复杂视觉排查用 High | 真实渲染结果、操作录像或截图、准确的验收记录 |

Terra 可以直接修改边界清楚的界面代码；Sol 也承担 UI 结构设计。播放器、Home 和屏保的跨生命周期改动由 Astra 统一审阅，避免把高风险行为分散修改。

## 4. 动态背景架构与验收

### 4.1 现有代码接入点

- `MainActivity` 当前直接承载 `HomeView`；`WallpaperLoader` / `WallpaperSource` 加载静态位图。
- `MarcoDreamService` 是另一条系统屏保路径；应用内时钟屏保也必须核对，不能只接通其中一条。
- `AppearanceSession` / `PreviewPreferences` 管理外观编辑草稿，保存取消规则继续复用。
- 不把视频逐帧读回 Bitmap 再交给桌面 Canvas 绘制。

建议新增独立视频控制器、背景容器、素材元数据与缓存管理器。具体类名和播放器依赖在 P0/P3 确定。项目使用自定义构建脚本，选用任何媒体库前先确认 Android 6、依赖体积与打包方式，不默认迁移 Gradle。

### 4.2 Astra 必须确定的边界

1. 比较 SurfaceView 与 TextureView 的叠层、首帧、性能及透明桌面组合，实测后确定默认实现。
2. 区分“用户希望播放”“页面可见”“屏幕亮起”“Surface 就绪”“首帧已到达”，不能只靠一个 playing 布尔值。
3. 生命周期至少覆盖：静态、准备、播放、暂停、释放、失败回退。每次准备使用会话标识，旧回调不得启动新页面已经取消的视频。
4. 桌面、系统 Dream 和预览之间明确播放器所有权；最多一个活动视频解码器，不让屏保与桌面同时抢硬解资源。
5. 打开影视应用或关屏后释放播放器。禁止为壁纸持有阻止休眠的锁，也不启动无限后台播放服务。
6. 不申请音频焦点，使用静音播放。影视应用声音、语音遥控器及音量键不受影响。
7. Home 服务关闭、应用被杀和播放器被释放是不同状态。视频恢复不得改写无障碍服务或绕过用户暂停桌面恢复的选择。

### 4.3 画质和视觉

- 初始基线：1080p SDR，24/30 fps。依据素材实际版本和设备解码能力选择，不假设所有素材都有全部清晰度。
- 4K 只作为通过解码与实机性能检查后的可选档位；弱设备保留 720p / 静态回退。
- 全程保留静态封面，首帧就绪再显示视频；失败时保持可操作桌面。
- 屏保返回“冻结当前帧”先验证截帧成本和色彩一致性；若代价过大，使用预生成封面过渡，不能为了追求完全连续引入黑屏或卡顿。
- Magic Desktop 使用封面参与 3D 预览和朦胧背景；播放预览独占同一个解码预算。
- 暗度、背景模式等设置复用现有风格。第一版不提供会造成额外耗电、掉帧的任意慢放。

### 4.4 Sol 的导入与缓存任务

- 手机上传需沿用已配对权限；设大小、格式、时长与剩余空间限制，不接受任意路径写入。
- 临时下载 / 上传文件校验成功后才原子提交；取消编辑、传输中断和失败都能清理临时文件。
- 正在播放、已保存及编辑草稿引用的资源不可被缓存回收误删。
- 下载需支持取消、有限重试；若提供断点续传，验证 Range 与内容版本，不能拼接不同文件。
- 首版建议默认缓存上限 512 MB，提供清理入口；这是初始产品值，按素材实际大小再调整。
- 备份保存模式与素材描述，不默认把大视频打进备份；恢复后素材缺失时明确回到静态背景。
- 视频 URL、完整本地路径和手机上传文件名不进入自动诊断报告；只记录允许的错误代码。

### 4.5 Apple 航拍专门门槛

Apple 视频能被播放器解码，与是否允许在公开 Android 软件中使用、缓存或再分发，是两项独立结论。Aerial 的直连下载实践只能作为技术参考。

评估时记录素材来源、版本、视频参数、相关条款及仍未确定的部分。不要把 Apple 视频复制进 APK、GitHub Release 或镜像站，也不要将项目 GPL 声明套用于这些素材。直连和仅供个人使用都不能作为已获得许可的证明。

若公开使用条件尚未明确，通用本地视频功能可以独立完成；Apple 专用目录入口保持待评估。是否开放按核实后的具体条件决定，不以模型推测代替授权证据。

## 5. 天气与定位架构

### 5.1 天气数据

建议路径：电视客户端 → 独立天气接口 → 服务商。

初选和风天气，Open-Meteo 作为可评估的备用提供方，不在首版默默切换来源。实施时重新核对服务条款、额度、缓存规则与署名。先用模拟响应完善流程，账号就绪后再验证真实接口。

服务端与现有反馈接收端隔离路由、配置和存储职责。凭据仅放服务器加密配置，不放 APK、源码或手机页面。设置来源允许列表、请求超时、返回大小限制、限流、配额熔断和费用上限；不允许客户端传任意上游 URL。

缓存以城市及请求类型区分，同城请求尽量合并；初始刷新目标为 30 分钟，最终遵守供应商规则。屏幕关闭时不做定时唤醒拉取，回到前台发现过期再刷新。返回服务商数据时间、抓取时间、来源和过期状态。

客户端保留上次成功数据，明确“更新于……”；长期过期时不能继续冒充实时天气。超时、429、无效响应、解析失败、城市切换期间旧请求返回都要验证。

### 5.2 定位顺序

1. 用户开启天气后，可选择“推荐所在城市”或手动搜索。
2. 服务端根据请求网络位置提供候选城市；返回识别来源和不确定状态，用户确认后保存。
3. 网络定位错误或缺失时，使用手动城市 / 区县搜索；保留省份以区分重名城市。
4. 手机定位作为后续便捷方式，在 HTTPS 页面由用户主动授权一次，反查城市后仅同步用户确认的城市标识。
5. 手机授权拒绝、定位超时、返回国外代理出口等情况，仍能手动选择城市。

网络城市推荐响应不能被跨用户公共缓存，否则可能把某人的城市返回给另一个人。天气数据缓存和定位结果缓存必须分开。

电视保存城市标识、名称和时区，不保存持续精确定位轨迹；精确坐标仅在反查所需流程短暂使用，避免写日志。定位用途和服务商需在开启界面说明，并允许关闭和清除城市。

### 5.3 手机配对与 HTTPS 的边界

现有局域网 HTTP 控制页不能被假定具有浏览器定位能力；HTTPS 页面也不能被假定可以直接访问局域网 HTTP 电视接口。

Astra 在 P0 明确其中一种通道：已有配对会话扩展，或独立的短时城市同步票据。若用云端票据，应具备随机不可猜测、用途限定、短时过期、单次消费以及电视确认；手机只提交城市，电视通过出站 HTTPS 获取。票据失效能重试，不在公网开放电视端口。

第一版若该通道未完成，先交付网络推荐和手选城市，不把“扫码打开网页”算作手机定位同步已完成。

### 5.4 界面

- 首页日期旁或下方显示城市、天气图标和温度，用户可关闭。
- 详情使用小气泡：体感、湿度、风力、未来三天、更新时间和符合条款的来源署名。
- 气泡与 Wi-Fi 等入口保持尺度一致；返回关闭当前层，焦点回到天气入口。
- Magic Desktop 中提供显示位置、字号和信息密度；遵守草稿保存取消规则。
- 使用离线示例数据预览样式时明确标识“预览”，不能混为真实定位结果。

## 6. 文件责任与交接规则

| 范围 | 主要所有者 | 约束 |
| --- | --- | --- |
| MainActivity / HomeView / MarcoDreamService 与新视频控制器 | Astra 设计并落地核心，Sol 后续按约定接入 | 修改生命周期、资源释放和跨页面所有权须交回 Astra 审阅 |
| 新天气服务端、天气客户端、新缓存与素材仓库 | Sol | 接口约定后实施，失败状态可测试，不引入 UI 线程网络或文件操作 |
| PersonalizationPanel / AppearanceSession / BackupStore / PhoneManager | Sol 统一整合 | 多任务不得同时编辑；共享设置键和迁移由一人负责 |
| 天气气泡、素材选择、手机页面、帮助与展示 | Sol 首次实现；Terra 后续拥有约定的局部 UI 文件 | Terra 在同一时间不与 Sol 修改同一文件 |
| 性能采样、异常归因、核心回归结论 | Astra | 分清本地模拟、模拟器与真实电视结果 |
| 定义好的遥控器流程、视觉截图与手机操作检查 | Terra | 报告具体设备、版本和结果，不用截图替代帧时间测量 |

默认按阶段串行切换模型，不要求同时启动多个代理。需要并行时，只能拆天气后端与独立的视频模块，先冻结共享接口并划清文件所有权；共享目录中的其他修改不得回退。

每次交接至少写明：基线提交、已修改文件、接口和设置键、已通过测试、失败项、实机状态、下一步动作。未实测的品牌明确标为待测。

## 7. 验收清单

以下是待执行计划，不代表已通过。

- [ ] 原有静态模式的桌面滚动、页面返回和 3D 预览保持正常。
- [ ] 天气正确处理拒绝定位、重名城市、网络失败、限流、过期数据和切换城市竞态。
- [ ] 手机定位只把确认城市绑定到对应电视，错误票据 / 过期票据 / 重放被拒绝。

## 8. 发布条件与当前下一步

天气服务商账号、真实接口费用、国内连通性、Apple 素材公开使用条件，以及不同电视的视频解码能力，均需实际核验。

正式发布需使用新的版本号和递增 versionCode，不能用同名 0.15.0 开发包替换线上安装包。GitHub、镜像、软件内更新的下载与校验值需一致；产品页只有对应功能已发布且素材经过隐私处理后才更新展示。

P0 已由 Astra 完成：两项纯 Java 核心策略、接口与持久化约定、既有桌面性能基线和本地回归，详见[核心交接](动态壁纸与天气核心交接.md)。下一步切换 Sol 完成 P1/P2，再回到 Astra 执行 P3；视频播放器与实时天气尚未接入，也未发布新安装包。
